# M17.4 · Render-layer diagnostic cap (defense-in-depth)

**Status:** todo
**Goal:** M17
**Size:** small
**Origin:** [M17-root-causes.md §3 ticket 2](../goals/M17-root-causes.md)

## What

[`internal/report/Render`](../../internal/report/report.go#L17) and [`internal/report/RenderJSON`](../../internal/report/report.go#L34) have no output cap. A 223,305-diagnostic SC-1 cascade (M17.1's worst case) marshals to a multi-MB JSON payload that crosses the WASM worker boundary, and prints 223k caret blocks to a CLI that the user cannot read. M17.3 closes SC-1 at the parser layer, but the rendering surface is the user-visible bottleneck — *any* future cascade (a shape we haven't probed, a regression of an existing gate, a new diagnostic emitter) hits the renderer with no backstop. The render-layer cap is the defense-in-depth that doesn't depend on every emitter staying well-behaved.

Cap both `Render` and `RenderJSON` at **500 diagnostics**. Past 500, omit the rest and append a single tail entry naming how many were suppressed. Sort first (existing [`sortDiags`](../../internal/report/report.go#L69) call), then truncate — the user gets the 500 lowest-offset diagnostics, which corresponds to "fix the earliest problems first."

## Scope

- **Add a package-level constant in [`internal/report/report.go`](../../internal/report/report.go):** `const MaxRenderedDiagnostics = 500`. Documenting the value here keeps the cap discoverable and avoids threading a new `RenderOptions` field through `RenderJSON` (which takes no options today; changing its signature ripples to four call sites in [cmd/voidslice/main.go](../../cmd/voidslice/main.go), [cmd/voidslice-wasm/main.go](../../cmd/voidslice-wasm/main.go), [internal/server/server.go](../../internal/server/server.go), and the report tests).

- **`Render` (pretty output).** After [sortDiags](../../internal/report/report.go#L21), if `len(sorted) > MaxRenderedDiagnostics`, render the first 500 as today, then append one trailing line of the literal form:

  ```
  ... and 222805 more diagnostics suppressed (render cap: 500)
  ```

  No file/line prefix, no caret block — a single bare line separated from the 500th entry by a `\n` (matching the inter-entry separator at [report.go:26-27](../../internal/report/report.go#L26-L27)). The suppressed count is `len(sorted) - MaxRenderedDiagnostics`.

- **`RenderJSON` (machine output).** Cap the `Diagnostics` array at 500 entries. Add a top-level field to [`jsonReport`](../../internal/report/report.go#L138-L141):

  ```go
  type jsonReport struct {
      File        string     `json:"file"`
      Diagnostics []jsonDiag `json:"diagnostics"`
      Truncated   int        `json:"truncated,omitempty"`
  }
  ```

  When `len(sorted) <= 500`, `Truncated` is 0 and the `,omitempty` keeps the field out of the serialized payload (no churn for the common case — the WASM oracle's strict byte-equality at [worker/harness/oracle.mjs:153](../../worker/harness/oracle.mjs#L153) sees identical output on clean files). When over the cap, `Truncated = len(sorted) - 500`.

- **Add tests in [`internal/report/report_test.go`](../../internal/report/report_test.go):**
  - `TestRender_CapAt500` — feed 501 synthetic diagnostics, assert the pretty output contains exactly 500 caret blocks and one trailing `... and 1 more diagnostics suppressed (render cap: 500)` line.
  - `TestRender_UnderCapNoTail` — feed 499 diagnostics, assert no `suppressed` line appears.
  - `TestRenderJSON_CapAt500` — feed 501 synthetic diagnostics; unmarshal the output; assert `len(Diagnostics) == 500` and `Truncated == 1`.
  - `TestRenderJSON_UnderCapNoTruncatedField` — feed 1 diagnostic; assert the JSON output does not contain the substring `"truncated"` (the `omitempty` contract).

## Dependencies

None. Independent of M17.3, M17.5, M17.6, M17.7. Lands in parallel with M17.3 — the parser fix and the render cap address the same UX bottleneck at different layers.

## Verification

- `go test ./...` clean; `go vet ./...` clean.
- The four new `TestRender*_Cap*` and `TestRenderJSON*_Cap*` sub-cases pass.
- `make harnesses` clean. In particular, [`worker/harness/oracle.mjs`](../../worker/harness/oracle.mjs)' byte-equality check between native CLI and WASM continues to pass on the standard corpus (no clean file in the corpus produces >500 diagnostics today).
- Manual: on a corrupted file that produces >500 diagnostics, `voidslice lint <file>` ends with the `... and N more diagnostics suppressed (render cap: 500)` line and prints 501 lines total (500 entries × N caret-lines plus 1 trailing summary; visually verifiable in a screenful).

## Out of scope (intentionally deferred)

- Making the cap configurable via a CLI flag or `RenderOptions` field. The flat constant is the simplest contract and the defense-in-depth job is done at any reasonable value; a user-facing `--max-diagnostics` flag is a separate UX decision and not required by M17's surprise classes.
- Capping at the parser/lint layer. The cap intentionally sits at the rendering surface so the parser remains free to emit accurately during recovery — the cap is about user-visible output, not engine truth.
- WASM-side renumbering of `Truncated` (e.g. "showing 500 of 223305"). The JSON shape already carries enough information for a client to compute the total (`len(diagnostics) + truncated`); UI text is the consumer's choice and out of M17's engine scope.
