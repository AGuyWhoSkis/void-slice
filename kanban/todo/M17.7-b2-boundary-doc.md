# M17.7 · B2 boundary — surface inherent limits in user-facing copy

**Status:** todo
**Goal:** M17
**Size:** small
**Origin:** [M17-root-causes.md §3 ticket 5](../goals/M17-root-causes.md)

## What

M17 is bounded by two principles: B1 (linting UX should be as pleasant as possible) and B2 (a linter can only do so much). The B2 half of the framing has an output deliverable: surface the inherent-limit principles named in [M17-root-causes.md §2](../goals/M17-root-causes.md) in copy the user can actually see. This is the "document what can't be fixed" half of M17 — it closes the user-perceived UX gap by setting expectations rather than by changing the engine.

At minimum, surface **P-AcceptedByteSet** (SC-4's principle: bytes outside the grammar's ASCII set in an uncommented region produce `VOID_SCAN` even when those bytes were author-intended UTF-8 in a comment). M17.6's investigation may add a second principle name (most likely **P-ProportionalToStructuralReach** — small textual edits can have large structural footprints when they change the file's parse shape). If M17.6 lands a fix-shape outcome instead, P-ProportionalToStructuralReach is dropped from this ticket and only P-AcceptedByteSet ships.

Two surfaces: the WASM playground's diagnostic-rendering area, and the `voidslice lint --help` text.

## Scope

- **Playground footer.** Edit [`web/src/components/DiagnosticsList.tsx`](../../web/src/components/DiagnosticsList.tsx) (the surface where edit→delta surprise actually bites users, per the goal's framing). Add a small, dismissible footer or expandable "Linter limitations" disclosure below the diagnostics list. Copy is:

  > **Linter limitations**
  >
  > - **Non-ASCII bytes in code positions** trigger scan errors. A comment containing non-ASCII characters (e.g. accented letters in author notes) will produce errors if uncommented — the linter can't tell that the bytes were author-intended.
  > - *[Second bullet inserted iff M17.6 lands the proportional-to-structural-reach verdict.]* **Small edits can produce many errors** when they change the file's parse shape. A single quote-byte flip can extend an orphan string literal across multiple following statements — the diagnostic count reflects the structural reach of the edit, not the edit's byte count.

  Wire it as a static `<details>` element under the existing `<ul className="vs-diags-list">` block at [DiagnosticsList.tsx:17-33](../../web/src/components/DiagnosticsList.tsx#L17-L33). Use the existing `vs-diags-*` CSS naming convention; a new class `vs-diags-limitations` is fine. Show the footer in both empty and non-empty diagnostic states — it documents the linter, not the file.

- **`voidslice lint --help`.** Edit [`cmd/voidslice/main.go`](../../cmd/voidslice/main.go) `usage()` at [main.go:36-41](../../cmd/voidslice/main.go#L36-L41) and the `lint` flagset at [main.go:43-82](../../cmd/voidslice/main.go#L43-L82). Add a `Limitations:` block to the `--help` output:

  ```
  Limitations:
    Non-ASCII bytes in code positions produce scan errors. Comments
    containing non-ASCII characters (e.g. accented letters) will
    error if uncommented.
  ```

  Implement by extending the flagset's `Usage` function so `voidslice lint --help` (and `voidslice lint` with no args) prints the block after the existing usage line. If M17.6 lands the proportional-to-structural-reach verdict, prepend the second bullet to the block in the same style.

- **Do not touch [README.md](../../README.md).** The user explicitly excluded README from this ticket's surfaces (see goal-slice decision) — the playground (point-of-use) and `--help` (point-of-action) are where the limits bite, and the README is reference rather than runtime copy.
