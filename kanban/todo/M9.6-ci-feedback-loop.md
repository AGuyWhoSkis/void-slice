# M9.6 · CI-feedback loop

**Status:** todo
**Goal:** M9
**Size:** small

## What

Formalize the protocol where an agent on a goal branch reads its PR's check status, fixes failing checks, and re-pushes — without human in the inner loop. The mechanism (PR-activity subscription + check-runs read) already exists via the GitHub MCP tools; M9.6 documents the protocol so an agent picking up a goal mid-session enters the loop without rediscovery, and integrates it as a step in `/implement-ticket` so it's not skipped.

## Scope

- **CLAUDE.md addition.** Short subsection (2–4 sentences) under the existing tooling docs naming the CI-feedback loop as the closing step of any ticket: after pushing, the agent watches CI; on failure, the agent fixes in-scope issues and re-pushes; on green, the agent proceeds to close. The text references the GitHub MCP tools (`subscribe_pr_activity`, `pull_request_read get_check_runs`) by name so the agent knows what to reach for.

- **`/implement-ticket` step added.** New step inserted between current step 7 (VERIFY) and step 8 (GAPS), called something like **PUSH & WATCH**. Behavior:
  1. Push the goal branch.
  2. If no PR exists for the goal branch, prompt the human to open one (or open it via `gh pr create` / MCP `create_pull_request` — implementer's call).
  3. Subscribe to PR activity for that PR.
  4. Read current check-runs status.
  5. If green: continue to GAPS.
  6. If failing: classify each failure as **in scope** (caused by this ticket's changes) or **out of scope** (pre-existing flake, infra, unrelated regression).
     - In-scope: fix, commit, re-push, loop back to step 4.
     - Out-of-scope: surface to human, do not attempt fix.
  7. **Stuck-loop guard:** if the same failure shape recurs twice without progress (i.e. the agent's fix attempt produced the same failure), surface to human rather than continuing to loop.

- **No new slash command.** `/ci-watch` or similar would be marginal value (saves one tool-call to find the PR number). Listed in out-of-scope for follow-up if friction accumulates.

- **Renumber `/implement-ticket` steps.** GAPS becomes step 9; CLOSE becomes step 10. Internal cross-references updated.

## Dependencies

Soft on M9.3 (PRs exist on per-goal branches, integrated with `/implement-ticket`'s flow). Soft on M9.5 (branch protection makes CI status meaningful — without it, an agent could merge through a red CI). Neither strictly blocks; M9.6 documents protocol that works regardless.

## Verification

- `CLAUDE.md` includes the CI-feedback-loop subsection naming the MCP tools and the in-scope/out-of-scope distinction.
- `.claude/commands/implement-ticket.md` includes a PUSH & WATCH step between VERIFY and GAPS, with the classification, retry, and stuck-loop-guard rules spelled out.
- An agent running `/implement-ticket` on a ticket that breaks CI reads the failure, fixes it in scope, re-pushes, reaches green, and then proceeds to GAPS — without human prompting.
- An agent encountering an out-of-scope CI failure surfaces it instead of attempting a fix.

## Out of scope (intentionally deferred)

- `/ci-watch` slash command — defer until friction proves it's worth saving the find-PR-number step.
- Auto-opening PR on first push — could live in M9.4 or a follow-up; not M9.6's concern.
- Classifying failures via static rules (e.g. "test name X = always flaky") — manual judgment is fine at this scale.
- Cross-PR coordination (e.g. "wait for M9.5 PR to merge before re-running CI on M9.6 PR") — there's no scheduler in this goal.
