# M7.4 · Post-deploy smoke + auto-rollback

**Status:** todo
**Goal:** M7
**Size:** medium

## What

The `production-deploy` job ([.github/workflows/ci.yml:191-231](../../.github/workflows/ci.yml#L191-L231)) currently treats a successful `wrangler deploy` as success. But Wrangler can deploy successfully while the deployed Worker fails to boot (e.g. a wasm import that errors at module-load, a syntax error masked by the bundler, a missing binding). M7.4 adds a smoke test against the freshly-deployed prod Worker; on smoke failure, it rolls the Worker back to the previous version automatically rather than leaving prod broken until a human notices.

## Scope

What must end up true:

- After the prod Worker deploy step in [.github/workflows/ci.yml](../../.github/workflows/ci.yml), a smoke step runs against the deployed prod Worker URL. The smoke test, at minimum, hits `/health` and exercises one `/lint` request with a fixture that should produce a known, non-empty diagnostic set.
- If the smoke step fails (non-2xx, body mismatch, timeout), a rollback step runs that returns the Worker to the immediately-prior version (using `wrangler rollback` or the equivalent versions API).
- The job fails (non-zero exit) on smoke failure, even if rollback succeeds — a human must see that something went wrong; CI green for a rolled-back deploy is misleading.
- Rollback is restricted to the prod Worker. Pages deploys are not rolled back — an unhealthy prod Worker is the failure mode worth automating; an unhealthy Pages deploy manifests differently and is out of scope.
- The smoke fixture lives somewhere stable (e.g. `worker/smoke/` or reuse a small file from `testdata/corpus-mini/`) so reviewers can read what's being checked.
- The job's logs make it obvious which step failed and what the rollback did. The PR / commit author shouldn't have to spelunk to know whether prod is on the new or old version.

Out of scope: smoke for Pages, smoke for preview deploys (preview is exercised by the reviewer), alerting / paging beyond the GitHub Actions failure notification, multi-step canary / staged rollout.

## Dependencies

Useful (but not strictly required) to land after M7.2 — once origin lockdown is in, the smoke step's curl needs to send an allowed `Origin` header. Note this in the implementation.

## Verification

- Land the change; the next merge-to-`main` runs the smoke job and it passes.
- One-off drill: open a scratch PR that intentionally breaks the deployed Worker (e.g. throws inside `ensureWasm`). Merge it. Confirm: the prod-deploy job's smoke step fails, the rollback step runs and reports success, the job exits non-zero, and a curl against the prod Worker URL still returns the prior (working) version. Revert the breakage in a follow-up PR.
- `make harnesses` and `go test ./...` pass — no Go changes here, but they should remain green.
