# M9.2 · Overlap surfacing in `/goal-define`

**Status:** todo
**Goal:** M9
**Size:** medium

## What

Wire two changes into `.claude/commands/goal-define.md`:
1. The skill prompts for and writes `**Paths:**` into the goal file.
2. The skill scans active/ongoing goals' `Paths:` and surfaces overlap in chat *before* drafting the file body, so the human catches collisions while scope is still cheap to redraw.

Surfacing is informational — the human decides whether to proceed. Blocking is `/goal-dispatch`'s job (M9.4); definition can produce overlapping goals if the human has reason.

## Scope

- **§2 conversation extended.** After the existing scope-and-exclusions discussion, the skill drafts a `Paths:` block from the prose answer (translating "touches `internal/scan/`" prose into `internal/scan/**` globs) and confirms the block with the user. Format follows the schema set in M9.1.

- **Overlap check runs after Paths confirmation, before file draft.** The skill:
  - Lists all `kanban/goals/M*.md` files.
  - Reads each goal's `**Status:**` and `**Paths:**` fields.
  - Filters to goals with status `active` or `ongoing` (excludes `parked` and `done` — they don't represent in-flight work).
  - For each filtered goal, computes whether any path in the working tree matches a glob from both that goal and the new goal. (At M9.2's scale — handful of goals, handful of paths each — the agent computes this by inspection. The canonical script implementation lives in M9.4.)
  - Reports overlaps in chat with the format: "Overlap with M{N} ({status}): `<glob>` (this goal) ↔ `<glob>` (M{N})" per match. If clean, says so explicitly: "No overlap with active or ongoing goals."

- **Goal file template updated.** The drafting block in `goal-define.md` includes a `**Paths:**` block between `**Scope:**` and `**Status:**`:
  ```markdown
  **Paths:**
  - <glob>
  - <glob>
  ```

- **No behavior change to mechanical steps.** File write to `kanban/goals/M{N}.md` and README row insertion are unchanged.

- **Re-running the conversation flow on existing M9 not required.** M9's Paths field is added by M9.1 directly; M9.2's behavior applies to *future* `/goal-define` invocations.

## Dependencies

M9.1 (schema must exist; otherwise nothing to read or write).

## Verification

- `.claude/commands/goal-define.md` step §2 prompts for and confirms a `Paths:` block.
- The drafting template includes `**Paths:**` between `**Scope:**` and `**Status:**`.
- Running `/goal-define` on a hypothetical goal with paths overlapping M9's surfaces (e.g. `kanban/**`) surfaces the collision in chat naming M9 and the conflicting glob.
- Running `/goal-define` on a goal with no overlap explicitly says so.
- The skill does *not* block on overlap — it surfaces and continues.

## Out of scope (intentionally deferred)

- Canonical script for overlap computation — lives in M9.4 with the dispatcher. M9.2 has the agent compute overlaps by inspection. A future follow-up may refactor `/goal-define` to call M9.4's script.
- Auto-deriving Paths from prose without confirmation — too magical; the agent drafts, the user confirms.
- Validating that declared Paths actually match files in the working tree — separate "Paths lint" concern.
