# M4.12 · wasm/worker corpus parity differential

**Status:** todo
**Goal:** M4
**Size:** small

## What

The wasm-built linter (`cmd/voidslice-wasm/`, `worker/`) is a separate build of the same Go code; in principle its diagnostics should match the native binary byte-for-byte. In practice, build flags, `wasm_exec.js` boundaries, and worker-side post-processing can drift. M4 lands a lot of new grammar surface — five new walkers and a new dispatch layer — and the existing differential oracle (M8.4 per CLAUDE.md) should be extended to cover the corpus. This ticket adds a wasm-vs-native differential check on a sampled `testdata/golden/` subset so wasm drift can't hide behind native-only test coverage.

This is the **wasm/worker-layer golden coverage** ticket.

## Scope

- Extend `make harnesses` (or the existing M8.4 differential oracle) to run the wasm linter and the native linter on a sampled corpus subset and assert byte-for-byte equality of the diagnostic output (pretty + JSON).
- Sample size + selection criteria decided at PLAN time. Constraint: at least one representative per in-scope shape (1, 2, 3, 5, sidecar) plus the existing `.entities` file.
- Failure surfaces the diverging file + diff so the wasm-side gap is locatable.

## Dependencies

M4.3–M4.8 (the corpus needs to be substantially drained of false positives so the differential isn't dominated by parse noise). Can land in parallel with M4.9.

## Verification

- `make harnesses` runs the new differential and passes on the sampled corpus subset. **wasm/worker-layer golden coverage** — wasm output ≡ native output, byte-for-byte.
- `go test ./...` green; CI's existing `make harnesses` gate keeps the differential green on every PR.
