# M12.17 · Layout-dependent diagnostic codes in recovery

**Status:** todo
**Goal:** M12
**Size:** small
**Origin:** M12.15 — F5/F6 in `lexinvariance-report.md`

## What

The M12.15 lexinvariance harness surfaced a same-shape divergence on
`testdata/cascades/missing-mid-file-brace/minimal.decl`:

```
baseline codes: [PARSE_UNTERMINATED_OBJECT, VALIDATE_ARRAY_INDEX_OOB]
variant  codes: [PARSE_EXPECTED_SYMBOL,    VALIDATE_ARRAY_INDEX_OOB]
```

Variant: `TransformReindent` v1 (strip leading whitespace) or
`TransformInterTokenPadding` v0 (collapse gaps). Same logical
structural error — a missing mid-file `}` — but the diagnostic code
changes from `PARSE_UNTERMINATED_OBJECT` (with message "unterminated
object") to `PARSE_EXPECTED_SYMBOL` (with message "expected '}' to
close component block"), purely based on whether intervening bytes
contain newlines/indent vs collapsed whitespace.

A user reading two whitespace-equivalent files should see the *same*
diagnostic code for the *same* structural error. Code stability across
trivial layout shifts is a soft contract the linter should keep.

This shape is distinct from M12.16 (which is about cascade *count*).
Here the count is preserved — it's the *identity* of the code that
diverges.

## Scope

- Trace which parser branch produces `PARSE_UNTERMINATED_OBJECT` vs
  `PARSE_EXPECTED_SYMBOL` for the same structural failure. The
  divergence is probably in how lookahead distinguishes "still inside
  an object, hit EOF" from "reached a sibling token before closing
  brace".
- Decide canonical code: which one better describes "missing `}` mid-file"?
  Probably `PARSE_UNTERMINATED_OBJECT` — that's what M12.12's anchor
  routing was tuned to emit. Pin that choice in a test.
- Pin the regression with a small fixture-level test that lints both
  the source and a whitespace-stripped variant; assert code multisets
  are equal.

### Out of scope

- F1/F2 and F3/F4 shapes — separate tickets.
