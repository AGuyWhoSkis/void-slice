# M12.8 · Locality on missing `{` after `=` (assignment-as-block typo)

**Status:** todo
**Goal:** M12
**Size:** small/medium
**Origin:** M12.7

## What

When a user writes `key =` and forgets the opening `{` of an object value
on the next line, the parser silently accepts the next identifier as the
assignment's value, then cascades downstream when it hits the structural
mismatch. The actual fault is invisible in the diagnostic list.

Discovered while reviewing M12.7 follow-ups, with this sample:

```
Version 1                                            <- 1
component {                                          <- 2
	cpntTest myTest {                                <- 3
		edit =                                       <- 4  ← missing `{` after `=`
			m_items = {                              <- 5
				num = 3;                             <- 6
				item[0] = { m_val = "a"; }           <- 7
				item[1] = { m_val = "b"; }           <- 8
				item[2] = { m_val = "c"; }           <- 9
			}                                        <- 10
		}                                            <- 11
	}                                                <- 12
}                                                    <- 13
```

Today's diagnostics (5 of them, none naming the real fault):

```
5:11  PARSE_EXPECTED_SEMICOLON     expected ';' after assignment
5:12  PARSE_UNEXPECTED_TOKEN       unexpected token in object body   ← the stray `=`
5:14  PARSE_UNEXPECTED_TOKEN       unexpected token in object body   ← the orphaned `{`
12:2  PARSE_UNEXPECTED_TOKEN       unexpected token at top level     ← cascade
13:1  PARSE_UNEXPECTED_TOKEN       unexpected token at top level     ← cascade
```

What happens:
1. `walkStatement` reads `edit`, sees `=`, calls `parseValue`.
2. `parseValue` accepts the next IDENT (`m_items`) as a `ValIdent` — a
   legitimate scalar value (e.g. `m_flag = true;`).
3. `walkStatement` then looks for `;` and finds `=` → first cascade diag.
4. Recovery falls through `walkObjectBody`'s default case, eating the `=`
   and the `{` as garbage. The brace stack is now off by one.
5. Two stray `}` end up at top level → final cascade diags on lines 12-13.

After the fix: a single focused diagnostic anchored at line 4's `=`
(or the IDENT that was misread as a value), naming the missing `{`. The
downstream cascade (lines 12-13) should disappear because the parser
recognizes the value as an object body and consumes the matching `}`s
correctly.

### Then: the fix

- **Layer:** parser ([`internal/parse/parse.go`](../../internal/parse/parse.go)).
- **Two candidate approaches** (pick during implementation):
  - **Lookahead in `walkStatement`'s assignment path.** After
    `parseValue` returns a non-object scalar value (`ValIdent` /
    `ValNumber` / `ValString`), peek the next token. If it's `=`, the
    "value" was actually a key whose `{` is missing — emit
    `PARSE_EXPECTED_SYMBOL` (or a new `PARSE_MISSING_OPEN_BRACE`)
    anchored at the original `=` token, suppress the downstream
    `EXPECTED_SEMICOLON`, and recover by treating what we have as an
    object body: rewind one token (back to the IDENT we mis-consumed)
    and resume `walkObjectBody` until we find the matching `}`.
    Cleanest because the fault detection happens at the call site that
    has full context (the just-consumed `=`).
  - **Heuristic in `parseValue` itself.** When `parseValue` sees an
    IDENT and the *following* token is `=`, refuse to consume it as a
    scalar — return a sentinel `Value{Kind: ValMissing}` and let
    `walkStatement` synthesize the diagnostic. More invasive (touches
    the value layer) but keeps `walkStatement` simpler.
- The fix must keep the M12.7 fixture (and the indent-aware close path)
  passing — the recovery shouldn't mis-trigger when the user really did
  mean an IDENT value (e.g. `m_flag = true;` followed by another
  statement on the next line).
