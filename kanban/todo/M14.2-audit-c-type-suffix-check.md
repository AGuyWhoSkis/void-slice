# M14.2 · Audit C — `inheritedDecl` type-suffix check

**Status:** todo
**Goal:** M14
**Size:** medium

## What

Evaluate the surviving intra-file diagnostic candidate from [`kanban/goals/M14.md`](../../kanban/goals/M14.md) — "`inheritedDecl` type-suffix consistency with the enclosing component" — for shippability under M14's partial-context constraint, and ship it (or document why not) into §3 of the spike memo.

**Rule choice is deliberately deferred to this ticket.** Corpus sampling showed that `inheritedDecl` lives inside `entity { entityDef name { ... m_componentDecls = { item_add["HASH"] = { inheritedDecl } } } }` blocks, not inside `component { cpntFoo name { ... } }` blocks — so "enclosing component" admits more than one definition. M14.2's first deliverable is the rule survey: enumerate 2–4 plausible intra-file rule shapes ("same `item_*["H"]` hash → same `.cpntfoo` suffix file-wide" / "inside `component { cpntFoo … }` only" / "any `inheritedDecl = "X.<suffix>"` where `<suffix>` lexically appears as an identifier sibling in the same object" / etc.), measure TP and FP for each against [`testdata/golden/`](../../testdata/golden/) using a throwaway script at `/tmp/m14-audit-c/`, and pick the rule with non-zero TP and zero FP. If none qualifies, that itself is §3's verdict.

Ship the diagnostic iff:
- **FP rate is empirically zero** on [`testdata/golden/`](../../testdata/golden/) (the linter's existing real-game-files bar — same standard the M4 allowlist drained against).
- **It degrades gracefully under partial context.** The rule must be a pure function of the parsed token stream; no dependency on filename or on sibling `.decl.xml` presence. The check is unaffected by the partial-context constraint per [`kanban/goals/M14.md`](../../kanban/goals/M14.md), which is one of the reasons it survived the filter — verify, don't re-derive.
