# M7.5 · Repeat-lint response cache

**Status:** todo
**Goal:** M7
**Size:** small-to-medium

## What

Most playground users paste the same file repeatedly while iterating on prose elsewhere. The Worker re-runs the wasm linter on every request, even when the body and filename are byte-identical to the previous request from the same edge. M7.5 caches `/lint` responses keyed on the request body so a hot file lints once per (cache region, cache TTL) instead of once per request — saving CPU time inside the Worker isolate and shaving latency off the response.

## Scope

What must end up true:

- The Worker checks the Cloudflare Cache API (e.g. `caches.default`) for a cached response keyed on a content hash of `(filename, body bytes)` before invoking the wasm linter. On a cache hit, it returns the cached JSON without running wasm.
- On a cache miss, the Worker runs the linter as today, then stores the response in the cache with a documented TTL (a small number of minutes — long enough to amortize repeated paste-and-tweak cycles, short enough that a re-deployed linter version starts emitting fresh results soon).
- The cache key includes a version stamp tied to the deployed Worker version so a new deploy invalidates prior cache entries. This avoids the "fixed a bug in the linter, but the playground still shows the old result" failure mode.
- The cached response carries a header (e.g. `X-Voidslice-Cache: hit`) so a developer can confirm caching from `curl`.
- The cache path respects the rate limiter — cache hits do not bypass `RATE_LIMITER.limit()`. (If exempting cache hits is desirable for UX, document the chosen behavior in `worker/index.js`; do not silently bypass.)
- Caching applies only to `POST /lint`. `/health` is not cached. Methods other than POST and content types not in the existing allowlist are unchanged.
- Multipart and raw-body request paths share the same cache (the cache key is over the resolved `(filename, src)`, computed after both code paths converge).

Out of scope: a content-addressable store (R2/KV); per-user cache keys; cache invalidation APIs. The Cache API's edge-local, TTL-bounded model is sufficient.

## Dependencies

None on M7.x. Implementation should not edit the same lines as M7.2 — M7.2 changes CORS / origin handling at the response-headers layer; M7.5 changes the path before `ensureWasm()`. Keep the diffs orthogonal so the two PRs don't conflict.

## Verification

- `wrangler dev worker/index.js`; POST the same body twice. First response: `X-Voidslice-Cache: miss` (or absent). Second response: `X-Voidslice-Cache: hit`. Body of the two responses is byte-identical.
- POST a different body → cache miss; vary the filename only → cache miss. Vary nothing → cache hit.
- After preview deploy, repeat the curls against the preview Worker URL — same hit/miss pattern.
- Hit the rate limiter (POST in a loop) — cache hits still count against the limit (or, if the chosen design exempts them, the design choice is documented inline in `worker/index.js`).
- `go test ./...` and `make harnesses` pass.
